\section{Orin: Current Architecture and
Operations}\label{orin-current-architecture-and-operations}}

Author: Samuel Padilla\\
Documentation review: October 22, 2026\\
Scope: source implementation and operating boundaries; deployed behavior
requires evidence for the exact revision, images and configuration.

This overview supersedes the older fixed chat pipeline and in-memory
worker inventory descriptions. Detailed source-era examples remain
available in
\href{https://github.com/ILGSupreme/Orin/blob/4e90651cd37f5b21175a8e71342f946ba6626622/orin-cluster-current-architecture-and-operations.md}{the
prior revision}; they are historical, not current operating
instructions.

\hypertarget{platform-and-responsibilities}{%
\subsection{1. Platform and
responsibilities}\label{platform-and-responsibilities}}

Orin connects users with agents, generative models and executable
capabilities across local, edge and federated environments.
Kubernetes/k3s is the current deployment target, including Jetson and
standard Linux hosts.

\hypertarget{bootstrap-and-deployment}{%
\subsection{3. Bootstrap and
deployment}\label{bootstrap-and-deployment}}

\texttt{install\_orin.sh} bootstraps the initial k3s server, namespace,
RBAC, SSH and k3s-token secrets, configuration ConfigMap and persistent
storage. It deploys Memory, Cortex and Federation in that order and
waits for their rollouts.

Relevant installer defaults include namespace \texttt{orin}, Cortex
NodePort \texttt{30080}, Federation NodePort \texttt{30081}, registry
\texttt{orin-gw:5000}, image version \texttt{1.0.0} and configuration
path \texttt{/data/configuration}. These are source defaults, not
verified values for a running cluster. Review
\texttt{bash\ install\_orin.sh\ -\/-help} and the script before
installation; bootstrap changes hosts and services.

The standard and Jetson Dockerfiles define separate native runtime
requirements. Source image names alone do not prove multi-architecture
compatibility, GPU availability or a working native model runtime.
Validate each selected image digest on the intended host.

Cortex deployment commands manage worker inventory, SSH-based k3s agent
installation, node labels, pod deployments and service discovery
metadata. Inventory changes are distinct from changes to Kubernetes
nodes or workloads.

\hypertarget{natural-conversation-and-persistent-work}{%
\subsection{4. Natural conversation and persistent
work}\label{natural-conversation-and-persistent-work}}

Both \texttt{POST\ /chat} and natural turns through
\texttt{POST\ /terminal\_chat} use the same flow:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Harness resolves the user/session through Memory and persists input.
\item
  AgentRuntime interprets the turn using the configured inference
  gateway.
\item
  The turn can return an immediate reply and create durable tasks.
\item
  Ready tasks advance through bounded decisions, authorized actions and
  persisted observations. Dependencies restrict which tasks can proceed.
\item
  Completion cites successful observations from the current cycle or
  completed dependencies. A model assesses whether the evidence meets
  the outcome.
\item
  Results, questions and notices persist in Memory for polling and later
  turns.
\end{enumerate}

The old \texttt{harness.chat} stage sequence and separate terminal/chat
interpretation schemas are superseded. Natural terminal requests can
create persistent work. Explicit terminal slash commands are dispatched
directly before this flow.

Tasks advance round-robin within a goal rather than concurrently within
that goal. Clarification blocks dependent tasks while unrelated work can
continue. Feedback can reopen completed work and invalidate dependent
results.

Memory owns durable goals, revisions and expiring execution claims.
JobManager owns transient jobs and generic pipeline utilities; it is not
the source of truth for responsibilities. A completed transient job is
not proof that every task in a goal succeeded.

Uncertain in-flight actions are paused for reconciliation after
recovery. Cancellation does not undo effects or guarantee that an
already accepted backend operation stops.

Explicit schedules and local events wake bounded runs. Arbitrary event
connectors, calendar rules and external notification delivery are not
implemented by the goal loop itself. See
\href{https://github.com/ILGSupreme/Orin/blob/main/docs/cortex-agent.md}{the
runtime}.

\hypertarget{inference-and-executable-capabilities}{%
\subsection{5. Inference and executable
capabilities}\label{inference-and-executable-capabilities}}

InferenceGateway has separate \texttt{interpret}, \texttt{decide} and
\texttt{work} bindings. Configured routes may use local Primer,
discovered LLM services or an OpenAI Responses provider. A separate LLM
pod is not mandatory for Cortex-local inference. Provider-only reasoning
avoids eagerly initializing local native engines.

External inference is disabled by default. Operator enablement and an
external-allowed turn/goal privacy policy are both required. Model
output cannot authorize export. Goals retain their privacy policy and
private context must not leak through subsequent provider-enabled turns.

The built-in agent inventory includes analysis, summarization, input
description, local backend/job snapshots, node inventory and workloads.
Local inspection uses an explicit backend-free command context and an
allowlist. It does not inherit the user's selected command folder or
arbitrary arguments.

Additional configured tools require a healthy discovered Tool backend
with the advertised capability and actual execution contract.
Configuration does not create a search service. Current-information
requests require retrieval evidence.

Canonical messages can represent multiple modalities; actual support
depends on the ingress, adapter and model. The current provider adapter
accepts text and image input; arbitrary binary uploads, audio and video
are not implemented there. Image description requires a suitable work
inference route.

Cortex \texttt{/ready} reports inference route status, goal storage
errors, Primer status and inventory status. \texttt{accepting\_requests}
depends on inference readiness and absence of an agent storage error.

\texttt{ok:\ true} alone does not prove usable inference, healthy
inventory or successful end-to-end work.

Goal controls verify user/session scope. Caller-supplied identifiers and
namespace partitions are not a new authentication mechanism. Cortex and
Memory interfaces remain inside the trusted local administration
boundary.

\hypertarget{protocol-discovery-and-routing}{%
\subsection{7. Protocol, discovery and
routing}\label{protocol-discovery-and-routing}}

RuntimeMessages carry typed content parts. WorkPackets describe backend
tasks, routing hints and metadata; WorkResults distinguish accepted,
running, completed and failed work. Acceptance must be followed through
retrieval to a terminal result and assessed against the requested
outcome.

RouterService submits and retrieves discovered backend work.
BackendClient handles local service transport. Federation uses its own
client and sanitization boundary rather than exposing internal
BackendClient URLs.

Kubernetes discovery lists Services labelled
\texttt{orin.ai/backend=true} in the configured namespace, with role
label \texttt{orin.ai/role}. Relevant annotations include kind, model,
capabilities, modalities, priority, weight and visibility.
EndpointSlices supply ready endpoint counts, including empty/omitted
endpoint cases. Runtime health and capability data inform backend
selection.

Metadata is a routing claim, not authorization or evidence that a model
can complete a task. Exact selection and endpoint conventions are
defined in the discovery and routing modules.

\hypertarget{memory-and-node-inventory}{%
\subsection{8. Memory and node
inventory}\label{memory-and-node-inventory}}

Memory stores conversation, claims, summaries and prompt context as well
as agent goals, worker inventory and Federation records. Goals use
revision checks and expiring claims. Worker inventory uses
namespace/alias identity and revision-checked writes against one
authoritative Memory database.

The bootstrap control node comes from Cortex configuration. Worker
records load from Memory; local snapshots are refreshed for
inventory-dependent commands. Do not import SSH credentials by guessing
from Kubernetes objects. Inventory failures must be explicit rather than
appearing as an empty cluster.

Before upgrading, inspect effective \texttt{MEMORY\_BASE\_DIR}, mounts
and data location. Older images may have stored data outside the
intended PVC. Preserve a consistent SQLite backup and associated files
before replacing pods or changing mounts. Local-path storage is not
replicated storage or a node-loss backup.

Follow
\href{https://github.com/ILGSupreme/Orin/blob/main/docs/memory-storage-upgrade.md}{storage
upgrades} and
\href{https://github.com/ILGSupreme/Orin/blob/main/docs/node-inventory-api.md}{node
inventory}, including restoring old in-memory worker settings before
they are lost.

\hypertarget{commands-and-terminal-client}{%
\subsection{9. Commands and terminal
client}\label{commands-and-terminal-client}}

CommandRouter uses structured commands, folders and
\texttt{CommandContext}. Handlers receive \texttt{(ctx,\ args)}.
Backend-specific folders are derived from discovered services; use
\texttt{/commands} to inspect the actual current inventory.

Common navigation includes \texttt{/help}, \texttt{/commands},
\texttt{/cd}, \texttt{/render} and \texttt{/attach}. Deployment,
Cluster, Configuration and Federation provide scoped commands.
Administration remains an explicit user control; safe-command flags do
not expose every safe command to the autonomous agent.

\texttt{terminal-chat.py} defaults to \texttt{/terminal\_chat}.
Connection settings include \texttt{ORIN\_URL}, \texttt{ORIN\_ENDPOINT},
\texttt{ORIN\_USER\_ID}, \texttt{ORIN\_STREAM} and
\texttt{ORIN\_CHAT\_ONLY}. \texttt{ORIN\_SESSION\_ID} resumes a session;
\texttt{ORIN\_PRIVACY} selects the turn's inference privacy policy. The
client polls goals for results and questions, deduplicates notices and
shows the latest result on reconnect.

Streaming natural ingress currently returns the assembled reply rather
than incremental provider token streaming.

\hypertarget{federation-implementation-and-limits}{%

redemption, membership, Ed25519 identities, signed envelopes,
replay/expiry checks, signed heartbeats and capability publication.
Memory stores network/member/token/work records; identity keys and
nonce/cache files remain local.

Federation validates membership, signature, nonce/expiry and policy,
sanitizes the packet, submits through CortexBridge and persists a work
record. Cortex's direct ingress currently accepts LLM work only, even if
a network policy lists other work types. No agent-goal controls or local
administration authority transfer with membership.

Results clear internal backend identity and apply policy to exact models
and runtime metadata. Revalidate failure/error responses as well as
successful results before relying on public confidentiality.

Network/token administration lacks a complete authorization gate in the
current application. Result polling checks network policy but does not
authenticate a signed member on the GET path. Policy quota/concurrency
fields do not prove enforcement. The HTTP MVP is not a completed public
deployment security model.

Local public listing is not decentralized global discovery. Automatic
federated backend selection, independent remote-agent delegation,
volunteer bootstrap/ relay infrastructure and proposed peer protocols
remain future work. See the
\href{https://github.com/ILGSupreme/Orin/blob/main/docs/orin-federation-network-plan.md}{Federation
plan}.

\hypertarget{validation-and-next-experiments}{%
\subsection{12. Validation and next
experiments}\label{validation-and-next-experiments}}

Automated checks use real runtime/Memory logic with model, tool and
provider HTTP doubles, plus a local HTTP server for Kubernetes
discovery. A separate CPU job compiles GGUF grammars using the native
parser without model weights. See
\href{https://github.com/ILGSupreme/Orin/blob/main/docs/ci.md}{CI};
consult the exact commit's workflow for results.

The supplied June 5, 2026 checkpoint records a successful signed
Federation submit/poll flow with sanitized output. It is historical
evidence and does not validate the current code or deployed images.

The next useful acceptance experiment is a real read-only node/workload
request: prove the action executed, inspect its persisted observation
and verify the goal's answer against that evidence. Repeat
representative requests with the actual model, including denied/missing
capabilities and recovery.

Then validate real retrieval/provider routes where configured, terminal
behavior, inventory persistence and current Federation
submission/polling. Record remaining failures rather than weakening
authorization or evidence checks.

See
\href{https://github.com/ILGSupreme/Orin/blob/main/docs/cortex-agent.md}{the
runtime} and
\href{https://github.com/ILGSupreme/Orin/blob/main/docs/unified-agent-action-plan.md}{acceptance
plan}. Expand tools and remote delegation only after the local execution
and feedback loop is reliable.
